1. Introduction

Purpose: defines the test plan for IWAS v1.0: objectives, scope, strategy, resources, schedule and responsibilities.

Scope: quote generation, underwriting and KYC, policy issuance, renewal, endorsement, cancellation and reinstatement, payments and invoices, claims, fraud detection, settlement, workflow orchestration, notifications, admin, RBAC, audit, security and the web UI. Core actuarial model internals and third-party vendor systems are excluded.

References: SRS v2.0, SAD v2.0, RTM (docs/TRACEABILITY.md), Test Case Document v2.5 (docs/TEST_CASES.md), docs/DEVIATIONS.md, IRDAI standards, PCI-DSS, WCAG 2.1.

Definitions: IWAS, KYC, BPMN, RTM, SLA, CI/CD, UAT, c8 (Node.js coverage tool), axe-core (WCAG rule engine), p95 (95th percentile).

2. Test Items

  • Quote generation (quotes.js); underwriting / risk scoring and KYC (underwriting.js, customers.js)
  • Policy lifecycle, payments and documents (policies.js, payments.js, documents.js, pdf.js)
  • Claims, fraud detection, settlement (claims.js, fraud.js, settlement.js)
  • Workflow orchestration engine (src/workflow/); notification service (notifications.js)
  • Admin, users, RBAC, audit and security (admin.js, users.js, src/security/)
  • Web UI (public/)

5. Test Approach / Strategy

LevelHow
UnitPure functions called directly with node:test: fraud rules, settlement formula, risk scoring, date and number parsing, BPMN parser and expressions, resilience helpers, PDF writer, colour contrast
IntegrationEach module through its HTTP API against a fresh in-memory SQLite database with the real neighbouring modules; vendors replaced by adapters with outage, decline and timeout modes
SystemEnd-to-end flows over real HTTP (quote → KYC → underwriting → payment → policy → claim → fraud → BPMN approval → settlement → notification); every UI screen of every role rendered in jsdom
AcceptanceUAT with the team as business users at the final demo; sprint outcome videos

Types: functional; regression (whole suite on every push and pull request); performance (in-process p95 test in CI, k6 for a deployed environment); security (§5.1); accessibility (axe-core WCAG A/AA rules and a contrast check, automated); contract tests against the SAD API; coverage with c8.

Test-first for defects: every defect is reproduced by a failing test, committed, then fixed in a separate commit; the test stays as a regression check.

Entry criteria: stable build, npm ci succeeds, CI green on main, test cases reviewed.

Exit criteria: 100 % of planned test cases executed, 0 critical defects open, all acceptance criteria met, coverage at or above the CI minimums (statements 93 %, branches 80 %, functions 92 %, lines 93 %).

11. Assumptions & Dependencies

  • Vendor sandboxes are represented by built-in adapters
  • Test data is generated per test; UI tests use the seeded demo data
  • The CI/CD pipeline is operational before test execution starts

12. Suspension & Resumption Criteria

Suspend testing if: the environment is unavailable for more than 4 hours; the build is too unstable (blocks more than 30 % of test cases, as happened on 18-11-2026 when the app could not start); a critical security vulnerability is discovered.

Resume testing if: blocking defects are resolved; the environment is stabilised; the security patch is applied and verified.

13. Test Case Management & Traceability

The RTM maps every SRS requirement to its module, test cases, test file and status. Test case IDs follow TC-<Area>-<NN> and appear in the test names, so a CI failure points straight to the requirement. Examples: IWA-F-001 → TC-Quote-01..07; IWA-F-010 → TC-Policy-01..04; IWA-F-020 → TC-Claim-01..11; IWA-F-021 → TC-WF-01..03; IWA-NF-001 → TC-Perf-01/02; IWA-NF-005 → TC-UX-01..04; IWA-SR-001 → TC-Sec-TLS-01.
