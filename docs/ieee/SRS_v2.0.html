1. Introduction

1.1 Purpose

This Software Requirements Specification defines the functional and non-functional requirements, interfaces and verification criteria of the Insurance Workflow Automation System (IWAS): the end-to-end lifecycle of insurance policies, from quote generation and underwriting to claim settlement. Version 2.0 describes the system as delivered at the end of Sprint 4 and records how each requirement was verified.

1.2 Scope

The system covers:

  • Customer onboarding (single and agent bulk), KYC verification and quote generation
  • Automated underwriting with rule-based risk scoring and a manual review queue
  • Policy issuance with signed PDF documents, renewal with reminders, endorsement, cancellation with refund, reinstatement after lapse
  • Claim registration with document upload, fraud detection, configurable BPMN approval workflow, settlement and claimant notifications
  • Agent/broker portal, underwriter and adjuster work queues, admin dashboards, reports and an immutable audit log

Excludes: core reinsurance internals, third-party actuarial model internals, external banking settlement networks, and the legacy policy-administration bridge. Vendor services (KYC, payment gateway, email, SMS) are integrated through adapters.

1.3 Audience

Developers, QA engineers, system integrators, insurance operations staff, compliance auditors and assessment evaluators.

2. Overall Description

2.1 Product Perspective

IWAS is a web-based platform that orchestrates insurance business workflows. As built it is a modular monolith: one Node.js/Express application in which each service named in the SAD (quotes, underwriting, policies, payments, documents, claims, workflow, notifications, admin) is a separate module with its own data tables, communicating through service interfaces and an in-process event bus. External vendors (KYC provider, payment gateway, email and SMS) are reached through adapter objects that can be replaced by real clients.

2.2 Major Product Functions

  • Generate personalised quotes from age, income, coverage type, term, sum insured and tobacco use
  • Score application risk (0–100) and route high-risk applications to an underwriter
  • Verify customer identity (KYC) before any policy is issued
  • Issue, renew, endorse, cancel and reinstate policies; produce signed policy documents and GST invoices
  • Register and track claims with document upload; detect fraud; route claims through a BPMN multi-level approval; calculate and pay settlements
  • Notify customers by in-app message, email and SMS at every status change
  • Provide dashboards, CSV/PDF reports and a tamper-evident audit log

2.3 User Roles and Characteristics

RoleCharacteristics and needs
CustomerBuys and manages policies, files and tracks claims. Expects a simple UI and quick turnaround.
Agent / BrokerOnboards customers (also in bulk), quotes and applies on their behalf, sees only their portfolio.
UnderwriterReviews high-risk applications and the manual KYC queue. Signs in with MFA; sees unmasked identity data.
Claims AdjusterReviews claims with fraud indicators and documents, approves amounts, settles, exports the claims register.
Admin / OpsConfigures workflows and settings, manages users, monitors SLAs, approves high-value claims, reads the audit log. Signs in with MFA.

2.4 Operating Environment

Server: Node.js 22.13 or later (Windows, Linux or the provided Docker image), SQLite through Node's built-in node:sqlite. Client: current Chrome, Edge or Firefox on desktop, tablet or mobile. Continuous integration on GitHub Actions. Changed from v1.0 (cloud Kubernetes, PostgreSQL, Redis and Kafka); see Appendix A.

2.5 Constraints

IRDAI compliance; GDPR / data privacy; PCI-DSS for premium payments (IWAS never receives card data, only gateway tokens); TLS 1.2+ for all connections in deployment; BPMN 2.0 for workflow definitions.

2.6 Assumptions and Dependencies

KYC, payment, email and SMS vendors offer sandbox APIs; the system runs as a single process per deployment (the payment lock and event bus are in-process); secrets (DATA_KEY, JWT_SECRET, SIGNING_KEY_PEM) are provided by the environment wherever data must survive a restart.

3. External Interface Requirements

3.1 User Interfaces

Responsive single-page web UI with role-based screens for the five roles; WCAG 2.1 AA (skip link, labels, live regions, visible focus, AA contrast in light and dark themes); navigation in English and Hindi; guided claim filing with a progress tracker.

3.2 Hardware Interfaces

  • Server: any x86-64 machine or container host able to run Node.js 22
  • Client: desktop, tablet or mobile browser
  • Key storage: environment-provided keys (HSM or vault in production)

3.3 Software Interfaces

InterfacePurposeAs built
KYC provider (Aadhaar / PAN)Identity verificationAdapter with circuit breaker and retry; outages route to a manual KYC queue
Payment gateway (Razorpay / Stripe)Premiums, refunds, claim payoutsToken-based adapter (tok_success, tok_decline, tok_flaky); retries transient failures
Actuarial enginePremium calculationLocal rating engine; outage returns 503
Email (SendGrid) / SMS (Twilio)NotificationsProvider adapters with retry and an outbox record per channel
Document storage (S3-compatible)Signed PDFs and claim evidenceDocument store behind the same API (store, fetch, verify)

3.4 Communications Interfaces

REST/JSON over HTTPS (TLS 1.2 minimum when a certificate is configured, HSTS), JWT bearer tokens with server-side revocation, standard error envelope { code, message, traceId }, retry with exponential backoff and circuit breakers towards vendors.
