1. Introduction

1.1 Purpose

This document specifies the architecture and design of the Insurance Workflow Automation System (IWAS) as built at the end of Sprint 4.

1.2 Scope

Covers all user services: quote generation, underwriting and KYC, policy issuance and lifecycle (renewal, endorsement, cancellation, reinstatement), payments and documents, claims processing with fraud detection, BPMN workflow orchestration, notifications, administration, reporting and audit.

1.3 Audience

Developers, QA engineers, security auditors, instructors and maintenance teams.

IWAS, BPMN, KYC, RBAC, ADR (architecture decision record), PCI-DSS, TLS, SLA, CI/CD, JWT, TOTP, PII, STRIDE.

3. Architecture

3.1 Goals & Constraints

Goals: secure, reliable (99.9 % availability target), testable, and structured so that each service can later be deployed independently; scalable to 1M+ policies through horizontal scaling once split into services.

Constraints: IRDAI and GDPR compliance, PCI-DSS for payments (no card data in IWAS), BPMN 2.0 workflows, and a student team of five that must run, test and demo the whole system on laptops and in CI.

3.5 Chosen Architecture Pattern and Rationale

Modular monolith + event-driven communication + BPMN orchestration.

  • Each SAD v1.0 service is a module with its own router, service functions and tables. Modules call each other only through ctx.services interfaces and react to events, so the boundaries match the planned microservices.
  • The BPMN engine externalises claim approval rules: admins deploy a new workflow version without redeploying code.
  • ADR-1 (v2.0): microservices on Kubernetes with Kafka (v1.0 choice) was replaced by a modular monolith, because a five-person student team must run, debug and test the whole system on laptops and in CI with one command. Fault isolation is provided in-process (circuit breakers, notification failures isolated from claims). Consequence: one process; the payment lock and event bus are in-memory, so multiple instances would need a database lock and a real broker.
  • ADR-2: store user text as written and escape it on output (no input stripping), so data is never silently altered.
  • ADR-3: card data never reaches IWAS; the client sends a gateway token (PCI-DSS scope reduction).

4. Design

4.1 Design Overview

Modules with clear bounded contexts; each owns its tables. Synchronous calls go through service interfaces (ctx.services.*); state changes are published on the event bus (workflow.task.created, workflow.completed, customer.kyc_updated, policy.issued, policy.cancelled, policy.reinstated, claim.status_changed). Calls to vendors use retry with exponential backoff and circuit breakers.

4.3 API Design

Base path /api/v1. JSON in and out. All endpoints except /auth/*, /quote and /health need Authorization: Bearer <JWT>.

4.4 Error Handling, Logging & Monitoring

  • Standardised error envelope on every error: { code, message, traceId } (+ details where useful, e.g. the amount for 402 PAYMENT_REQUIRED).
  • HTTP status map: 400 invalid input, 401 unauthenticated / MFA required, 402 payment failed or required, 403 forbidden, 404 not found, 409 state conflict (e.g. PAYMENT_IN_PROGRESS), 413 too large, 422 business rule, 429 rate limited or locked, 503 vendor unavailable.
  • Structured JSON logs; PII redacted from every line; trace id per request (client ids validated to prevent log injection).
  • Health endpoint /api/v1/health used by the Docker HEALTHCHECK and CI; dashboard shows SLA breaches (tasks older than 48 h), claim backlog, failed payments.

4.5 UX Design

Role-based single-page UI; WCAG 2.1 AA (verified on every screen with axe-core; contrast in both themes); English and Hindi navigation; guided claim filing in three steps with a progress tracker; confirmation dialogs that state amounts before any payment or cancellation.

4.6 Open Issues & Next Steps

  • Split modules into services with a real broker if load requires it (boundaries already in place).
  • ML-based fraud scoring on top of the 8 rules; blockchain audit trail and native mobile app remain out of scope.
  • Production deployment: uptime monitoring, Prometheus/Grafana, WAF, secrets vault, OWASP ZAP scan.
  • Embed a Unicode font for Devanagari text in generated PDFs.
